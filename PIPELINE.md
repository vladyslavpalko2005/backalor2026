# Від скану до структурованого ключа

Реалізація повторює етапи на наданій схемі, але доступність автоматизації залежить від навчених моделей. Код інтеграції не є навченою моделлю й сам по собі не гарантує точності.

| Етап схеми | Реалізація в Backalor | Участь користувача |
|---|---|---|
| Digitised page image | Імпорт зображень і сторінок PDF | Вибір сканів |
| Preprocessing | Конструктор обробки, порівняння оригіналу й результату | Вибір кроків |
| Element detection | Рамки L3, евристична сегментація або каскад YOLO | Виправлення рамок; для YOLO потрібні відповідні ваги |
| Pair and structure detection | L1 секція → L2 пара → L3 елемент, перевірка вкладеності | Ручна розмітка або навчені L1/L2/L3 моделі |
| Plaintext / ciphertext role | Окрема властивість `text_role`, успадкування від батьківської рамки | Роль задається вручну; автоматичного визначення ролі немає |
| Element type classification | Окрема властивість `element_type`; класифікація вирізаних L3 | Ручний вибір або локальна YOLO classification модель з класами `readable`, `cipher_symbol` |
| Handwritten text recognition | TrOCR для L3 типу `readable` | Потрібна локальна модель TrOCR; результат перевіряється вручну |
| Cipher-symbol identification | Класифікатор L3 типу `cipher_symbol`; ім'я класу стає кодом символу | Потрібна модель, навчена на кодах цього набору символів, або ручне введення коду |
| Structured digitised key | Ключ JSON/CSV зі зв'язками L1/L2/L3, ролями, координатами та статусом перевірки | Перевірка й підтвердження елементів |

Каскад YOLO починає з L1, потім шукає L2 у вирізаних L1, а L3 — у L2. Схема концептуально описує ті самі об'єкти в іншому порядку; їхні геометричні рівні не потрібно міняти.

## Роль і тип — незалежні властивості

- **Відкритий текст + читабельний:** слово або літера з відкритої частини ключа → TrOCR.
- **Шифротекст + читабельний:** цифри або звичайні літери, які позначають шифр → також TrOCR.
- **Шифротекст + шифросимвол:** спеціальний знак → класифікатор кодів символів.

Значення «шифротекст» не означає, що елемент не можна прочитати як текст. Програма не вгадує роль за положенням зліва/справа. Роль можна встановити для L1/L2, тоді вона успадковується їхніми елементами; власна роль L3 має пріоритет. Не задавай одну роль всій парі L2, якщо вона містить обидві сторони ключа.

## Ручний процес без нових моделей

1. Імпортуй скани й створи/виправ L1 → L2 → L3 на вкладці **Розмітка**.
2. Вибери L3 → **Властивості**. Задай **Роль**, **Тип елемента**, транскрипцію для читабельного елемента або стабільний код для шифросимволу, наприклад `S001`. Натисни **Застосувати** або перейди до іншого елемента для застосування змін.
3. Відкрий **Перевірка / Kontrola**. Таблиця показує L3 поточної сторінки й відсутні дані. Подвійне натискання відкриває відповідну рамку у властивостях.
4. Перевір фрагмент на скані, вибери його рядок у таблиці й натисни **Підтвердити вибраний L3**. Підтвердити неповний елемент не можна.
5. Натисни **Експорт ключа…**, вибери JSON або CSV. Експорт охоплює весь проєкт. Збереження поточної сторінки відбувається перед експортом.

## Автоматична класифікація й розпізнавання

На вкладці **Перевірка** вкажи навчені локальні `.pt` файли для типів і/або символів. Модель типів має містити рівно два класи: `readable` і `cipher_symbol`. Модель символів повертає коди своїх класів. Звичайні ваги детектора `yolov8n.pt` для цих полів не підходять.

**Визначити типи L3** заповнює лише невизначені типи поточної сторінки. Результати нижче порогу залишаються невизначеними. Значення, які вже задано, зберігаються.

Для TrOCR встанови залежності у середовище редактора:

```bash
cd /Users/vladislave/Desktop/backalor-main
.venv-desktop/bin/python -m pip install -r requirements-ocr.txt
```

У **Інструменти → Моделі та навчання** вкажи папку локальної TrOCR-моделі з процесором і вагами. Код використовує `local_files_only=True` і сам моделі не завантажує. Для ML рекомендовано окреме середовище Python 3.12, сумісне з обраними версіями PyTorch/Transformers.

**Розпізнати L3 за типом** направляє читабельні фрагменти до TrOCR, спеціальні знаки — до класифікатора символів. Якщо відповідна модель не налаштована, ця гілка пропускається. Наявні транскрипції та коди не перезаписуються. Моделі завантажуються один раз на операцію. Робота виконується у фоні, редагування на час операції блокується.

Автоматично отриманий результат потребує ручного підтвердження. Для типу та коду символу зберігаються оцінка впевненості й джерело; їх можна побачити в підказках таблиці й експорті. Для TrOCR числова впевненість не вигадується: поле залишається порожнім. Оцінка класифікатора не є виміряною точністю на твоєму наборі.

## Дані для навчання класифікаторів

Кнопка **Навчальні фрагменти…** експортує перевірені L3 для типів елементів або кодів шифросимволів. Вибери порожню папку. Експорт створить `train/<клас>`, `val/<клас>`, `test/<клас>` та `manifest.json` з походженням фрагментів. Для кодів використовуй латинські літери, цифри, `_` і `-`.

Потрібно щонайменше три незалежні документи та щонайменше два класи, присутні в кожній частині набору. Сторінки однієї групи документа не потрапляють у різні частини. Це мінімальні вимоги до структури експорту, а не достатній обсяг для якісного навчання. Якщо даних мало, експорт пояснить причину відмови. Розподіл фіксований; неправильний баланс виправляється розміткою додаткових незалежних документів.

Навчання класифікаторів запускається окремо від кнопок навчання детекторів L1–L3. Приклад із локальними початковими classification-вагами та експортованим набором:

```bash
.venv-desktop/bin/python -m pip install -r requirements-ml.txt
.venv-desktop/bin/yolo classify train model=/path/to/initial-cls.pt data=/path/to/type-dataset epochs=50 imgsz=224 batch=8
.venv-desktop/bin/yolo classify val model=/path/to/trained/best.pt data=/path/to/type-dataset split=test
```

Так само навчається окрема модель кодів символів на її наборі. Навчені `best.pt` потрібно підключити на вкладці **Перевірка**. Офіційна документація: [Ultralytics image classification](https://docs.ultralytics.com/tasks/classify/).

## Структура ключа та перевірка

JSON зберігає сторінки, секції, пари L2 та масиви `plaintext`, `ciphertext`, `unassigned` з елементами L3. Пара може містити кілька елементів з кожного боку: програма не вигадує однозначних відповідностей між ними. Елементи без коректного L2 не губляться, вони потрапляють до `unpaired_elements`.

CSV містить рядок на пару; масиви елементів записані як JSON у відповідних клітинках. Елементи без пари та сторінки без анотацій мають окремі рядки. Для повного машинного представлення з усіма проблемами сторінки використовуй JSON.

Статус `ready` вимагає коректної геометрії, обох ролей у кожній парі, заповнених типів/результатів і ручного підтвердження всіх L3. Сторінки без анотацій утримують загальний статус `draft`. Чернетку теж можна експортувати: пропуски й причини збережено в `issues`. Статус `ready` означає проходження цих перевірок, а не доведену історичну правильність дешифрування.

Зміна ролі, типу, транскрипції, коду, батьківської рамки чи геометрії скидає підтвердження відповідних елементів. Нові поля підтримують автозбереження, чернетки відновлення, undo/redo, COCO та ZIP/серверні копії.

Поточний формат анотацій — `schema_version: 4`; окремі роль і тип з'явилися у версії 3, явні посилання символів на текст — у версії 4. Старі файли читаються без переписування при відкритті; при наступному збереженні використовується новий формат і створюється резервна копія. Старі `kind=plaintext/ciphertext` читаються як роль, `kind=symbol` — як тип шифросимволу. Тип читабельності з ролі не виводиться. Після ручного застосування властивостей старий змішаний `kind` замінюється окремими полями. Для редагування нового формату використовуй поточну версію редактора.
